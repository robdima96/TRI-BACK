# TRI-BACK Study Web Application — Build Specification (v2.2)

You are a senior full-stack developer. Build a **local-first Python web application** using the **Reflex** framework that serves as the participant-facing front end for the TRI-BACK musculoskeletal triage chatbot research study.

This is **not** a greenfield chatbot project. The conversational dialogue backend already exists under `bot/` (FastAPI + LangGraph). Your job is to build the **study shell**: authentication, group routing, admin controls, a shared chat UI, session logging, message feedback, and the **prototype infrastructure** for knowledge-graph traversal results — with clean seams so arm-specific presentation layers can differ while all arms share the same underlying pipeline.

---

## 1. Project context and constraints

| Item | Requirement |
|------|-------------|
| Framework | Reflex (Python), single deployable app |
| Hosting | Local development first (`reflex run`); structure for later LAN/tunnel deployment |
| Backend integration | Call the existing FastAPI service in `bot/` — do **not** reimplement conversational dialogue, encoding, or LangGraph orchestration |
| Repo layout | New app lives in `prototypes/tri_back_study_app/` — do not modify `bot/` internals except via HTTP |
| Session logs | JSON snapshots written to `prototypes/sessions/` (parallel to `bot/data/sessions/`) |
| Graph traversal | `bot/` queries red-flags v1 **locally** from `Graphs/backups/red flags/v1/` (no live Neo4j); study app consumes `graph_traversal` from `ChatResponse` |
| Python | Match `bot/` (3.11+ recommended) |
| Database | SQLite for users (study IDs + group assignment), login audit, and admin actions |
| UI reference | Match the blue-and-white professional style of `Graphs/app/` (see §5.5) |
| Scope | Research prototype — prioritize clarity, modularity, and auditability over production hardening |

### Shared backend pipeline (all three arms)

Every participant, regardless of `group_id`, uses the **same** `bot/` backend that:

1. **Conducts conversational dialogue** — multi-turn intake and triage-oriented questioning via LangGraph (`POST /api/v1/chat`)
2. **Encodes symptom entities** — pattern rules, NER, and safety phrases populate a **clinical checklist** each turn
3. **Traverses a knowledge graph** — checklist items and semantically retrieved chunks map to red-flag **Factor** nodes and walk paths (from the local v1 CSV graph) to **Condition** targets and triage disposition (e.g. seek emergency care vs manage conservatively)

The three experimental arms differ **only in what the participant sees** after this shared pipeline runs — not in which backend endpoint or orchestration path is invoked.

### Non-goals (explicitly out of scope for v1)

- OAuth, email verification, password reset flows
- One-time-use / account-locking (`used` flag) — replaced by detailed session logging (see §2.3)
- Live Neo4j connection inside `bot/` or the study app — graph traversal uses the **local v1 backup** (`Graphs/backups/red flags/v1/source/red_flags_manual_failsafe.csv`); the Neo4j explorer in `Graphs/app/` remains separate and unchanged
- Full Neo4j admin UI (reuse graph JSON contract from `Graphs/app/` only)
- Hosting on cloud infrastructure (document how, but do not implement)
- Clinical validation or changes to triage logic inside `bot/`

## 2. Authentication and user management

### 2.1 Login page

**Participants**

- Login form: study ID + password
- On failure: generic error ("Invalid credentials") — do not reveal whether the study ID exists
- On success: increment login count, record login timestamp, allocate next session ID (see §2.5), route to `/chat`

**Admin**

- Login form: username + password + **arm selector** (required toggle or radio group: Arm 1 / Arm 2 / Arm 3)
- The selected arm determines which chatbot presentation the admin experiences for this login session — admin is **not** bound to a fixed `group_id` in the database
- Admin has **unlimited sessions**; each login creates a new session (see §2.5)
- After login: route to `/chat` with the selected arm, with a link to `/admin` dashboard in the header
- Store the admin's arm choice for the session in Reflex state (`admin_selected_arm`)

### 2.2 Accounts

**Admin (hardcoded for v1, migration-ready)**

| Field | Value |
|-------|-------|
| username | `admin` |
| password | `tri-back` |
| role | `admin` |

Store admin credentials in a config module (`auth/config.py`) with a comment and interface stub for future DB-backed auth. Use a password hash (e.g. `bcrypt` or `passlib`) even for the hardcoded password. Track admin login count separately (SQLite `admin_meta` table or dedicated row) for `admin_{n}` session IDs.

**Participants (SQLite)**

- **90 unique accounts** pre-seeded via `scripts/seed_users.py`
- **Usernames are study IDs** — use the real study identifier strings supplied at seed time (e.g. from REDCap export), **not** generic placeholders like `participant_001`. Each row stores `study_id` as the login username alongside `group_id`.

```sql
CREATE TABLE users (
  id             INTEGER PRIMARY KEY,
  study_id       TEXT UNIQUE NOT NULL,   -- study identifier used at login; always written to logs
  password_hash  TEXT NOT NULL,
  group_id       INTEGER NOT NULL CHECK (group_id IN (1, 2, 3)),
  login_count    INTEGER NOT NULL DEFAULT 0,
  first_login_at TEXT,
  last_login_at  TEXT
);

CREATE TABLE login_events (
  id         INTEGER PRIMARY KEY,
  study_id   TEXT NOT NULL,              -- "admin" for admin logins
  role       TEXT NOT NULL,              -- "participant" | "admin"
  login_at   TEXT NOT NULL,              -- ISO-8601 date and time
  session_id TEXT NOT NULL,              -- e.g. 425_1 or admin_3
  group_id   INTEGER,                    -- participant arm from DB; admin selected arm at login
  FOREIGN KEY (study_id) REFERENCES users(study_id) ON DELETE SET NULL
);
```

- Generate random passwords (12+ chars) on seed; write a **one-time CSV** (`data/participant_credentials.csv`) with columns `study_id`, `password`, `group_id` — never log plaintext passwords after seeding

### 2.3 Login logging

On **every successful login** (participant or admin):

1. Increment `login_count` for that account (participants in `users`; admin in `admin_meta`)
2. Update `first_login_at` (if null) and `last_login_at` on the user row
3. Append a row to `login_events` with:
   - `study_id` — participant study ID, or `"admin"` for admin logins (**study ID must always be present and human-readable in logs**)
   - `role`
   - `login_at` — full ISO-8601 datetime (date and time)
   - `session_id` — the session ID allocated for this login (§2.5)
   - `group_id` — participant's assigned arm, or admin's selected arm at login

4. Write the same login metadata into the **session JSON** header (see below) so every `prototypes/sessions/sess_*.json` file is self-describing:

```json
{
  "session_id": "425_2",
  "study_id": "425",
  "role": "participant",
  "group_id": 2,
  "login_count": 2,
  "login_at": "2026-07-03T13:45:00-07:00",
  ...
}
```

Admin dashboard must display `login_count`, `last_login_at`, and a per-user login history table sourced from `login_events`.

### 2.4 Session logging and engagement metrics

Persist a **rich session snapshot per login session** to `prototypes/sessions/`, modelled on `bot/app/session_store.py`:

- One JSON file per session: `sess_{sha256(session_id)}.json`
- Atomic write via temp file + rename (same pattern as `bot/app/session_store.py`)
- Create `prototypes/sessions/.gitignore` ignoring `sess_*.json`
- **`study_id` is a required top-level field in every session file** — never omit or bury it

**Each snapshot must include:**

| Field | Description |
|-------|-------------|
| `session_id` | Deterministic ID for this login session (§2.5) |
| `study_id` | Participant study ID, or `"admin"` |
| `role` | `participant` or `admin` |
| `group_id` | Presentation arm for this session |
| `login_count` | Cumulative login number for this account at time of session start |
| `login_at` | ISO-8601 datetime of this login |
| `started_at` / `last_active_at` | ISO-8601 timestamps |
| `time_on_task_sec` | Cumulative active time (idle gaps > 60 s excluded; configurable) |
| `turn_count` | Number of user→assistant round-trips |
| `messages` | Trimmed transcript (cap at 40 turns) — see message shape below |
| `clinical_checklist` | Latest merged checklist snapshot from backend responses |
| `engagement` | Per-turn and aggregate metrics (see below) |
| `graph_traversal` | Latest `GraphTraversalTrace` payload (or `null` until backend provides it) |
| `citations` | Accumulated evidence chunks referenced across turns |
| `escalated` / `safety_reason` / `coverage_ready` | Latest safety and disposition flags |

**Message shape** (each assistant message that is visible in the UI):

```json
{
  "message_id": "msg_003",
  "role": "assistant",
  "content": "...",
  "reasoning_text": null,
  "has_graph": false,
  "citations": [],
  "timestamp": "2026-07-03T13:46:12-07:00",
  "feedback": {
    "rating": "up",
    "rated_at": "2026-07-03T13:46:45-07:00"
  }
}
```

- `message_id` — stable unique ID per visible assistant output (e.g. `msg_{turn_index}`); used for feedback
- `feedback.rating` — `"up"`, `"down"`, or `null` if not yet rated
- `feedback.rated_at` — ISO-8601 datetime when the participant last submitted feedback

**Per-turn engagement metrics** (append to `engagement.turns[]` on each user message):

- `turn_index`, `timestamp`
- `user_word_count`, `user_char_count`
- `composer_to_send_ms`, `round_trip_ms`, `idle_before_turn_sec`

**Aggregate engagement** (recomputed each turn):

- `total_user_words`, `total_user_chars`
- `mean_round_trip_ms`, `median_round_trip_ms`
- `session_duration_sec` (= `time_on_task_sec`)
- `feedback_up_count`, `feedback_down_count` — tallies across assistant messages in this session

Implement `prototypes/tri_back_study_app/session_store.py` with `load_session(session_id)` and `save_session(session_id, **fields)`. Call `save_session` after every successful chat turn, after every feedback click, and on logout.

### 2.5 Session ID strategy

Session IDs are **deterministic and human-readable** — not UUIDs.

**Participants**

- Format: `{study_id}_{n}` where `n` is the login/access count for that participant
- Examples: study ID `425` → first login session `425_1`, second login `425_2`, third `425_3`
- On each new login: increment `users.login_count`, set `session_id = f"{study_id}_{login_count}"`, create a **new** session file and LangGraph thread
- Within a single login session: reuse the same `session_id` until logout; pass it on every `ChatRequest` to FastAPI (aligns with LangGraph `thread_id`)

**Admin**

- Format: `admin_{n}` where `n` is the admin access count (unlimited sessions)
- Examples: `admin_1`, `admin_2`, `admin_3`, …
- Each admin login increments the admin access counter and allocates the next `admin_{n}` session ID
- Admin's `group_id` for the session comes from the **arm selector at login**, not from the database

**Implementation**

- `auth/session_ids.py`: `allocate_session_id(study_id, role, login_count) -> str`
- Persist current `session_id` in Reflex state / signed cookie for the active browser session
- Filename remains `sess_{sha256(session_id)}.json` (hash of the human-readable ID)

### 2.6 Role-based routing

| Role | Post-login destination |
|------|------------------------|
| `admin` | `/chat` with arm selected at login; header link to `/admin` |
| `participant` | `/chat` with `group_id` from SQLite |

Participants may reconnect during an active login session (same `session_id`). A **new login** always starts a fresh session with the next `{study_id}_{n}` or `admin_{n}` ID.

## 3. Experimental design — three presentation arms

### 3.1 Group assignment

- 30 participants per group (90 total)
- `group_id` ∈ {1, 2, 3} stored in SQLite alongside `study_id`
- Balanced assignment at seed time (30/30/30)
- **Blinding:** participants never see arm labels or group numbers in the UI
- **Admin override:** admin selects arm 1, 2, or 3 at login (§2.1) to preview any presentation variant

### 3.2 Arm definitions — identical pipeline, different visible output

All arms call the **same** `POST http://localhost:8000/api/v1/chat` endpoint. A **presentation adapter** keyed by `group_id` (participant) or `admin_selected_arm` (admin) decides what extra content is shown. The adapter does **not** fork the backend or orchestration.

| group_id | Arm name | Visible output (in addition to shared elements) |
|----------|----------|--------------------------------------------------|
| 1 | `baseline` | **Regular text response only** — exactly as returned in `ChatResponse.response` from `bot/` |
| 2 | `reasoning_text` | Regular text response **plus** a chain-of-thought-style narrative block explaining clinical reasoning steps derived from graph traversal |
| 3 | `graph_visible` | Regular text response **plus** an **inline Cytoscape knowledge-graph** showing the traversal path (see §5) |

**Shared across all arms (always visible):**

- Primary assistant reply text (`response`)
- **Citation chips** for evidence chunks traversed or retrieved — source + snippet on expand (all arms expose citations)
- **Thumbs up / thumbs down** controls on each unique visible assistant message (see §5.2)
- Escalation banner when `escalated=true`
- Identical input box, message history container, loading states, and layout chrome

### 3.3 Adapter interface

```python
class ChatbotAdapter(Protocol):
    async def send_message(self, session_id: str, message: str) -> ChatTurnResult: ...
```

`ChatTurnResult` normalizes `bot/app/schemas.py` `ChatResponse` fields plus presentation-layer fields from §4. Use a **factory** keyed by effective `group_id`. The factory always calls the same HTTP client; presentation adapters only control **rendering**.

### 3.4 Arm 2 — chain-of-thought reasoning text (prototype layer)

Build `prototypes/tri_back_study_app/graph/reasoning_formatter.py` that converts a `GraphTraversalTrace` + `citations` into human-readable numbered reasoning steps. Consume `graph_traversal` from `ChatResponse` once `bot/` exposes it (local v1 graph traversal).

### 3.5 Message feedback (thumbs up / down)

- Every **unique visible assistant output** renders a feedback row with thumbs-up and thumbs-down icons (or equivalent accessible buttons)
- One feedback record per `message_id`; participant may change their vote (up → down or vice versa) — latest vote wins
- On click: update `messages[].feedback` in session JSON immediately via `save_session()`
- Feedback is **optional** — `rating` may remain `null` if the participant does not rate
- Do not block chat while unrated; do not show feedback controls on user messages
- Include `feedback_up_count` / `feedback_down_count` aggregates in session JSON and admin session detail view

## 4. Knowledge-graph traversal (local v1 graph — consumed from `bot/`)

Graph traversal in `bot/` reads the red-flags v1 knowledge graph **locally** from disk — no live Neo4j required for the chatbot or study app. The interactive Neo4j explorer under `Graphs/app/` is a separate tool and is **not modified** by this build.

**Canonical graph source:** `Graphs/backups/red flags/v1/`

| File | Role |
|------|------|
| `source/red_flags_manual_failsafe.csv` | 66 rows — each row is a Chunk + Factor + Condition path segment |
| `inventory.json` | 48 Factors, 6 Conditions (CES, AAA, Fracture, Malignancy, Infection, DVT), chunk ids |
| `graph_model.json` | Schema reference (direct / mediated / both paths) |

The study app does **not** re-implement traversal. It consumes `ChatResponse.graph_traversal` (and related fields) returned by `bot/` after each chat turn.

### 4.1 Module layout (study app — presentation only)

```
prototypes/tri_back_study_app/graph/
  __init__.py
  schemas.py              # Re-export or mirror bot/app/services/graphrag/schemas.py
  traversal_client.py     # Thin HTTP passthrough: reads graph_traversal from ChatResponse
  reasoning_formatter.py  # Arm 2: CoT text from GraphTraversalTrace.steps
  cytoscape_builder.py    # Arm 3: ensure visualization payload shape
```

Remove `stub_traversal.py` — no mock graph synthesis in the study app; `bot/` is the source of truth.

### 4.2 Traversal client contract

```python
class TraversalClient(Protocol):
    def from_chat_response(self, response: ChatTurnResult) -> GraphTraversalTrace | None:
        """Parse graph_traversal dict from bot/ ChatResponse; no local graph query."""
```

During development before `bot/` exposes traversal fields, the adapter may return `None` and the UI falls back to text + citations only.

### 4.3 JSON contract

Align with `bot/app/services/graphrag/schemas.py` and `Graphs/app/lib/graphApi.js` (`GraphTraversalTrace.to_visualization_payload()`). Node labels: `Factor`, `Condition`, `Chunk`. Synthetic element IDs from local traversal are acceptable for Cytoscape rendering.

### 4.4 Citations (all arms)

Surface `ChatResponse.citations` as expandable chips. Citations must correspond to chunk ids (`r_1`…`r_66`) traversed or semantically retrieved by `bot/`. Include deduplicated citations in session JSON.

## 5. Chat UI — shared components, arm-specific output

### 5.1 Design principle

**All UI components are identical across arms** — same pages, same `chat_message.py`, same `citation_list.py`, same `feedback_row.py`, same composer. The **only** difference is which optional blocks render inside an assistant message bubble:

| Component | Arm 1 | Arm 2 | Arm 3 |
|-----------|-------|-------|-------|
| Primary response text | ✓ | ✓ | ✓ |
| Citation chips | ✓ | ✓ | ✓ |
| Thumbs up / down | ✓ | ✓ | ✓ |
| Escalation banner | ✓ | ✓ | ✓ |
| Reasoning text block | — | ✓ | — |
| Inline graph | — | — | ✓ |

### 5.2 Layout

- Header: TRI-BACK study title, **study ID** displayed prominently (participants see their study ID; admin sees `admin`), session ID in subdued text (e.g. badge)
- Message history: scrollable, newest at bottom
- Each assistant message: content blocks + citation chips + feedback row
- Composer: text input + Send; disable while awaiting response
- Loading indicator during backend round-trip
- Escalation banner when `escalated=true`
- Footer disclaimer: not for emergency use; if urgent symptoms, contact emergency services

### 5.3 Inline Cytoscape (Arm 3 only)

Render inside the assistant message bubble or directly below it — **no dedicated side pane**. Node colours match `Graphs/app/public/js/graph.js`. Graceful fallback if `graph_trace` is missing.

### 5.4 UX requirements

- Mobile-tolerant (min width 360px)
- Keyboard: Enter to send, Shift+Enter for newline
- Accessible feedback buttons with `aria-label` ("Helpful" / "Not helpful")
- Do not expose system prompts, checkpoint paths, or internal model names to participants

### 5.5 Visual design — match `Graphs/app/`

Replicate the clean blue-and-white professional aesthetic from `Graphs/app/public/css/styles.css`. Define shared CSS variables (or Reflex theme tokens) mirroring:

## 8. Configuration and run order

Document the full end-to-end setup in `README.md`. A developer must be able to go from a clean checkout to a working chat UI by following these steps in order.

### 8.1 Prerequisites

- **Python 3.11+**
- **Node.js 18+** (required by Reflex frontend toolchain)
- **Google Cloud SDK (`gcloud`)** — for Vertex AI Application Default Credentials
- Local model checkpoints on disk (paths configured in `bot/.env`):
  - **Clinical_sBERT** — RAG sentence embeddings (`TRI_BACK_ENCODER_DIR`)
  - **GliNER-BioMed** — span NER (`TRI_BACK_GLINER_MODEL_DIR`)
- **No Neo4j credentials required** for the study app or `bot/` chatbot — graph traversal uses `Graphs/backups/red flags/v1/` locally. (Optional: Neo4j in `Graphs/.env` is only for the separate `Graphs/app/` explorer — leave that tooling unchanged.)

### 8.2 Google Cloud / Vertex AI authentication

The generator backend is configured as `TRI_BACK_GENERATOR_BACKEND=vertex` in `bot/.env`. Vertex uses **user Application Default Credentials** — no JSON service-account key file.

**One-time setup:**

1. Install [Google Cloud SDK](https://cloud.google.com/sdk/docs/install) if not already present
2. **Do not set** `GOOGLE_APPLICATION_CREDENTIALS` — unset it if already defined:
   ```powershell
   Remove-Item Env:GOOGLE_APPLICATION_CREDENTIALS -ErrorAction SilentlyContinue
   ```
3. Authenticate with your Google account:
   ```powershell
   gcloud auth login
   gcloud auth application-default login
   ```
4. Set your GCP project (use the project ID from Cloud Console, not the numeric project number):
   ```powershell
   gcloud config set project YOUR_PROJECT_ID
   gcloud auth application-default set-quota-project YOUR_PROJECT_ID
   ```
5. Enable the **Vertex AI API** for the project in [Google Cloud Console](https://console.cloud.google.com/apis/library/aiplatform.googleapis.com)
6. Ensure billing is linked to the project in Cloud Console

**Verify ADC** (optional smoke script):

```powershell
cd bot
python scripts/vertex_adc_smoke.py
```

Or call `GET http://127.0.0.1:8000/ready` after starting the API — the `generator` check reports Vertex/ADC status via `bot/app/services/vertex_auth.py`.

ADC file locations:
- Windows: `%APPDATA%\gcloud\application_default_credentials.json`
- macOS/Linux: `~/.config/gcloud/application_default_credentials.json`

### 8.3 Configure `bot/.env`

Copy or edit `bot/.env`. Minimum variables for a full stack run:

```ini
# Model paths (adjust to your local directories)
TRI_BACK_ENCODER_DIR=E:\TRI-BACK\Clinical_sBERT
TRI_BACK_GLINER_MODEL_DIR=E:\TRI-BACK\GliNER-BioMed
TRI_BACK_LOAD_GLINER=1
TRI_BACK_LOAD_NER=1
TRI_BACK_LOAD_RAG=1

# Generator — Vertex AI
TRI_BACK_GENERATOR_BACKEND=vertex
TRI_BACK_GENERATOR_MODEL=gemini-2.0-flash-001
TRI_BACK_VERTEX_PROJECT_ID=your-gcp-project-id
TRI_BACK_VERTEX_LOCATION=us-central1

# Chroma RAG
TRI_BACK_CHROMA_PATH=data/chroma
TRI_BACK_CHROMA_COLLECTION=tri_back_evidence
TRI_BACK_ENCODER_DIM=768
TRI_BACK_RAG_TOP_K=10

# Session stores
TRI_BACK_SESSION_STORE_DIR=data/sessions
```

Do not commit secrets. Project ID is not a secret but keep `.env` local.

### 8.4 Install and prepare the `bot/` backend

```powershell
cd bot
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -e ".[dev,generator-api]"
```

**Ingest RAG evidence** (if `TRI_BACK_LOAD_RAG=1` and Chroma is empty):

```powershell
python scripts/chroma_clear.py --empty
python scripts/ingest_chunks.py --sub-collection red_flags --registry manual
```

See `bot/README.md` and `Knowledge Base/Red Flags/chunks/README.md` for the full extract → enrich → ingest pipeline.

## 9. Security and research hygiene

- Hash all participant passwords at rest
- HTTP-only session cookies; CSRF protection on mutating admin actions
- Rate-limit login attempts (simple in-memory counter acceptable for v1)
- Log admin actions with timestamp and target `study_id` (audit table)
- When `escalated=true`, ensure escalation text from backend is visible and not truncated
- Session files may contain PHI — `prototypes/sessions/` must not be committed
- `study_id` appears in SQLite, `login_events`, and every session JSON file for traceability

## 10. Acceptance criteria (definition of done)

- [ ] Admin can log in with arm selector; each login creates `admin_{n}` session

## 11. Implementation notes for the developer

- Prefer **async HTTP** (`httpx`) for FastAPI calls from Reflex event handlers
- On each turn: (1) call `bot/` chat, (2) parse `graph_traversal` from response for Arms 2/3, (3) format arm output, (4) `save_session()`
- Do not duplicate graph traversal in the study app — `bot/` loads `Graphs/backups/red flags/v1/` locally per `prototypes/temp_prompt_kgt.txt`
- On feedback click: update `messages[i].feedback` and recompute `feedback_up_count` / `feedback_down_count`
- On login: `allocate_session_id()` → insert `login_events` row → initialize session JSON with `study_id`, `login_at`, `login_count`
- Reference: `bot/app/main.py`, `bot/app/schemas.py`, `bot/app/session_store.py`, `bot/app/services/vertex_auth.py`, `bot/app/services/graphrag/schemas.py`, `prototypes/temp_prompt_kgt.txt` (local v1 graph traversal in `bot/`), `Graphs/backups/red flags/v1/`, `Graphs/app/public/css/styles.css`, `Graphs/app/public/js/graph.js`

## 12. Resolved design decisions (do not re-open unless requester changes)

| Decision | Value |
|----------|-------|
| Blinding | Participants never see arm labels |
| Account locking | **None** — session logging instead |
| Username format | Study IDs from roster CSV |
| Session ID format | Participants: `{study_id}_{n}`; Admin: `admin_{n}` (unlimited) |
| Admin arm | Selected at login via toggle; not fixed in DB |
| Login logging | `login_count` + `login_events` table + datetime; `study_id` in all logs |
| Message feedback | Thumbs up/down per visible assistant output, stored in session JSON |
| Backend | Single `bot/` endpoint for all arms |
| Citations | Exposed in all arms |
| UI style | Match `Graphs/app/` blue-and-white design tokens |
| Graph traversal | **Local v1 CSV** in `bot/` (`Graphs/backups/red flags/v1/`); study app displays `ChatResponse.graph_traversal`; `Graphs/app/` Neo4j explorer unchanged |
